四、本轮修复的真实缺陷

① ryzenadj 参数映射：原 `build_args` 只生成 `--stapm-limit/--ppt-limit`，与 power 区块真实语义不符。改为完整映射 --stapm-limit W*1000 --fast-limit W*1000+1000 --slow-limit W*1000 --apu-slow-limit W*1000 --slow-time 1 + --gfx-clk + --apu-sku 0。

② LS 状态解析哨兵值：grab(tag) 未命中时返回 "读取失败"，导致 or 回退失效。改为返回空串，使 LSFG2Mode / LSFG3Mode1 正确回退。

③ GPU 浮动在封顶误升压：当 gpu_current_freq == gpu（余量=0）时，余量≤100 误触发 +150。加 余量>0 守卫后，封顶低载正确降频。

④ 配置列表→字典归一：AppConfig.from_dict 用 dict(list) 误转 ProcMonConfigs 列表为损坏字典，下游崩溃。改为显式列表→{name:{Path}} 字典。

⑤ steam 进程识别：原判定 name == "steam" 匹配不到 steam.exe。改为子串匹配 "steam" in name.lower()。

⑥ 真实 LS 适配器缺 is_running()：LSBlock 在初始化即调用 self.ls.is_running()，但真实 LosslessScaling 适配器此前只有 Mock 有该方法——一旦接真机（备份目录含 LS设置）即 AttributeError 崩溃。已在真实适配器补上 is_running()（经 Win32ProcessManager 探测 LosslessScaling.exe，非 Windows/不可用安全返回 False）与 set_running() 对齐接口。

⑦ build_ryzenadj 引用不存在的 Win32RyzenAdj：当脚本目录存在 blocks/ryzenadj-win64/ryzenadj.exe 时工厂函数返回 Win32RyzenAdj(exe)，而该类从未定义（真实类名为 RyzenAdj），NameError 崩溃。已改为 RyzenAdj(exe)。

累计修复真实缺陷：7 项（①~⑦）。其中 ⑥⑦ 仅在接真机外部工具时触发，单测用 Mock 无法覆盖，已补 test_real_adapters.py 锁定。

六、GUI 卡顿 & 布局修复（本轮）

问题根因：首版 GUI 把每个区块的 refresh_panel / set_lock / update_status 都放在 UI 主线程 每秒跑一次，而 procmon / freeze / ls 的刷新会反复 spawn wmic 枚举进程、 ls 还会探测 LosslessScaling 进程——这些子进程阻塞主线程，叠加起来就是「非常卡」。

修复方案：

① 重活搬后台线程：新增 _RefreshWorker(QThread)，每 2 秒在后台线程跑一遍 procmon / freeze / ls 的 refresh_panel 与 power 的 gpu_float_tick（读 GPU 占用）；UI 主线程只跑一个 1 秒的轻量 sync() 重绘（只读缓存状态，不 spawn 进程）。rtss.set_lock / power.update_status 本就很轻，留在主线程。

② 跨线程安全：sync() 永远只在主线程执行（经 _SyncBridge 的 QueuedConnection 桥接， 不用 lambda 直接接 worker 信号）；toast 适配器（_Label/_Toast）把 setText/show/ setStyleSheet 用 QTimer.singleShot 派回主线程，使后台线程里的 show_toast 也安全。

③ 关闭不崩：原实现把 QThread 父级挂到窗口、且用 lambda 在 worker 线程里直接 sync()， 进程退出时原生崩溃（RC=127）。改为 worker 不挂父、closeEvent 里 quit()+wait() 干净收尾。

④ 布局：窗口改为 372px 宽、右上角停靠（贴任务栏上方）；卡片内边距/间距收紧；procmon / ls 的按钮列表改为 内部滚动（限高 150px），不再无限撑高窗口；冻结面板的「候选/已冻结」分段标题在列表为空时自动隐藏； 磁贴用固定 4 列网格。

验证：offscreen 端到端实测——重刷新落在 Dummy-2 工作线程（非主线程）， 同时 100ms 心跳在 2.6s 内稳定触发 23 次，证明后台 0.3s 刷新完全不阻塞 UI 线程； 新增 test_heavy_refresh_runs_off_main_thread 锁死该行为。pytest 全绿 81 passed。

八、ryzenadj 跨进程互斥加固（2026-07-28 · 对标 EC 安全模型）

来源：分析老牌掌机工具 MotionAssistant 的底层 EC 并发安全模型——EC 用 EcMutex 系统级命名互斥防止多线程/多进程并发读写字节端口（IBF 清空 / OBF 置位前必须抢到锁、最多重试 RW_MAX_RETRIES=5 次），避免误写或卡死。该思想可直译为「对全局 ring0 驱动（WinRing0）的访问必须跨进程串行化」。

加固前：并发守卫仅 _RYZENADJ_CALL_LOCK（threading.Lock()），只能拦进程内多线程 （GPU 浮动 / CO / 手动点击）。拦不住「两个 凝冰结魄 实例」或「凝冰结魄 + GPD 工具 / MotionAssistant / 别的 ryzenadj 调用方」跨进程并发抢 WinRing0——这正是崩溃-重启竞态的跨进程残留风险。

加固后（双层互斥）：

① 进程内：保留 _RYZENADJ_CALL_LOCK + _RYZENADJ_BUSY，拦同进程重入（Windows 命名互斥同线程可递归重入，故进程内仍靠此标志）。

② 系统级：新增 _SYS_MUTEX = ctypes 命名互斥 Global\NingBingJue_RyzenAdj_WinRing0， try_acquire() 超时 1.5s；持锁中二次获取返回 busy → 本轮调用 SKIP（不阻塞、不雪崩）。 silent 路径下互斥由 _reap_silent 持有到子进程 ryzenadj.exe 退出才释放，覆盖整个 WinRing0 生命周期。

③ 降级：非 Windows / 互斥创建失败 → 自动 degraded 降级为 no-op，仅留进程内锁，不致命。

验证：py_compile 通过；tests/test_platform.py 全绿（5 passed，较原 4 增 1 条 named-mutex 用例）；用 multiprocessing 起独立进程持锁 → 主进程 try_acquire 返回 busy，子进程释放后主进程 acquired（XPROC_MUTEX_OK），证明真正跨进程串行化。

边界：命名互斥只能拦「也遵守同一把锁」的调用方。GPD 官方 utility、MotionAssistant 等不合作外部工具不会尊重它， 「别同时跑别的 ryzenadj 工具」仍是铁律——此层互斥主要补掉「自己多开」与「未来统一走一个 launcher」的洞。 真根因（ReBAR 已关、进程内孤儿堆积已修）已解决，此属中低优先 hardening。

仍有价值的设计提醒：MA 的 EC 文档同时强调「动态热循环完全不碰电压 / Curve Optimizer」—— 真正危险、会导致 WHEA / 欠压崩 / 键盘冻住的是电压类 CO 操作（最坏发生在轻载）。 本仓库负载门控 CO 的「默认 -20 / -50 双重硬门控 / 无游戏=0 / 30s sticky」门控必须保死，切勿为激进省电放松。
