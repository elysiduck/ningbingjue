辉光呼吸根治重构报告

凝冰结魄 · HUD 呼吸灯 · 彻底免去「每帧整窗重绘」 · 2026-08-29

一句话结论

此前已把「重绘范围」从「整棵控件树」缩到「一层缓存位图」、并把呼吸节拍从 40ms 降到 50ms，掌机仍有残余卡顿。根因是：半透明辉光层每帧 update() 都会触发 Windows DWM 对整个窗口表面的 Alpha 混合，分数 DPR(1.5×) 还会放大像素惩罚。本次根治把辉光提成「独立的顶层窗口」，呼吸/暗化改用 setWindowOpacity——由 DWM 在合成阶段做 alpha 乘法，不重新光栅化任何像素，每帧 CPU 开销趋近于 0。

① 为什么「开了呼吸灯」还会卡？（通俗易懂）

把呼吸辉光想象成窗户上贴的一层「半透明彩色玻璃」。每一帧，Windows 都要把这层玻璃和后面的桌面重新「叠」一遍颜色（Alpha 混合）。问题不在于「画了什么」，而在于「它是半透明的、而且每帧都要重叠」：

  • 呼吸灯是 WA_TranslucentBackground 的半透明层，整窗大小。
  • 呼吸以 ~20–25fps 持续触发 ov.update() → 辉光缓存位图 blit + DWM 整窗重混。
  • 掌机是 分数 DPR 1.5×（1080p@150%），这块半透明面被放大，混色像素更多 → 更慢。
  • 滚动时再叠加重绘 → 卡顿最明显（之前修的「滚动冻结」只缓解了、没根除）。

WorkBuddy / 普通软件没有这种「常驻半透明动画层」，所以滚动顺滑——这正是差异来源。

② 旧架构：每帧 update → DWM 整窗重混

即便「只 blit 一层缓存位图」，只要窗口是半透明的，DWM 仍要在每一帧重新把整块表面与桌面合成。这是「半透明 + 每帧重绘」的固有税。

③ 新根治：辉光提成独立顶层窗，脉搏交给 windowOpacity

关键点：辉光位图只在「尺寸/DPR/颜色」变化时烘焙一次（_rebuild_glow_cache，按 1.0 满亮）。呼吸与失焦暗化只是把窗口整体 alpha 乘上一个系数，由 DWM 在合成阶段完成——这一步不碰像素、不进 CPU 渲染管线。

④ 为什么还要「拆」出一个边框/蒙版层？

setWindowOpacity 调制的是整窗 alpha——如果边框和编辑蒙版和辉光挤在同一个窗口，它们会被一起「呼吸」。但：

  • 托盘白边（alpha 55）需要失焦时保持（原设计就是「边框不随失焦变暗」）；
  • 编辑蒙版（暗色叠加）需要编辑期间保持恒定，保证控件对比度——一旦随呼吸脉动，编辑器文字会忽明忽暗。

所以把「托盘边框 + 编辑蒙版」拆到新的 _GlowBorderOverlay 独立窗口（windowOpacity 恒为 1.0，只在几何/主题/编辑态变更时重绘）。辉光窗只管「呼吸」，边框/蒙版窗只管「稳定」。两者都由主窗拥有、位于主窗之上、编辑蒙版之下。
